# Decisions

One line each: `D-NN: decision — reason — step`. Later steps depend on these; change one only with a new entry that supersedes it.

- D-01: License is GPL-3.0-or-later; contributions under DCO (`git commit -s`), no CLA — libntfs-3g is GPL-2.0-or-later and links in-process, so the whole is a GPL work — Step 01
- D-02: Platform is macOS 27+ on Apple Silicon (arm64 only, `ARCHS = arm64`) — macOS 27 brings the FSKit Handler protocols, KOIO and `FSClient.mountSingleVolume`, and has no Intel support — Step 01
- D-03: Names: product `Unlatch`, CLI `unlatch`, FS short name `unlatch`, engine prefix `ue_` — `ntfs` is Apple's name and collides; `ntfs_*` collides with libntfs-3g symbols — Step 01
- D-04: `BUNDLE_PREFIX` is `io.github.ramanan-bala` (app `…Unlatch`, extension `…Unlatch.FSModule`, App Group `group.…Unlatch`, log subsystem `…unlatch`) — matches the GitHub account `Ramanan-Bala` that hosts the public repo — Step 01
- D-05: `Unlatch.xcodeproj` is generated by XcodeGen from `project.yml` and not committed (it is in `.gitignore`); `Scripts/bootstrap.sh` regenerates it — one source of truth, no merge conflicts in `project.pbxproj` — Step 01
- D-06: Builds are ad-hoc signed for now, and the entitlements files (`App/Resources/Unlatch.entitlements`, `Extension/Resources/UnlatchFSModule.entitlements`) are kept in the repo but not referenced from `project.yml` — App Group and `com.apple.developer.fskit.fsmodule` need a provisioning profile, and ad-hoc builds fail with them; Step 08 must add a team and reference them before the extension can load — Step 01
- D-07: Swift packages use `swift-tools-version: 6.0` (Swift 6 mode, complete concurrency checking) with `platforms: [.macOS("27.0")]`; CLI depends on `swift-argument-parser` `from: "1.5.0"` (resolved 1.8.2, `CLI/Package.resolved` committed) — reproducible CLI builds — Step 01
- D-08: The FSKit extension target is an XcodeGen `extensionkit-extension` with `EXExtensionPointIdentifier = com.apple.fskit.fsmodule`; the app embeds it and the scheme `Unlatch` also builds `UnlatchEngine` and `unlatch-engine` — one `xcodebuild -scheme Unlatch build` covers every Xcode target — Step 01
- D-09: libntfs-3g is pinned to release 2026.9.28 (latest stable; the plan expected 2022.10.3). It is vendored as the release tarball from tuxera.com (SHA-256 `350d9415…f295c8`, matching the release notes), extracted into `Engine/vendor/ntfs-3g/`, and recorded in `Engine/vendor/VERSION` — the tarball ships a generated `configure`, so no autotools are needed, and it fixes several CVEs found since 2022 — Step 02
- D-10: libntfs-3g is configured with `--disable-ntfs-3g --disable-mount-helper --enable-ntfsprogs --disable-crypto --disable-plugins --disable-nfconv --disable-shared --enable-static`, plus `--exec-prefix` so nothing installs to `/bin` or `/lib`. `--disable-nfconv` means the library does no NFC/NFD conversion itself, so the host normalizes names to NFC (B4). `--disable-plugins` means no `dlopen` of reparse plugins in the extension — Step 02
- D-11: `libntfs-3g.a` is merged into `libUnlatchEngine.a` (`OTHER_LIBTOOLFLAGS`), so the extension and `unlatch-engine` link the one engine archive. The ntfs-3g include path is set on the `UnlatchEngine` target only — Step 02
- D-12: `Scripts/build-ntfs3g.sh` builds out of tree, from a copy in `build/ntfs3g-src` with `Engine/vendor/patches/*.patch` applied, so the vendored tree is never modified. `Scripts/bootstrap.sh` runs it when `build/ntfs3g/lib/libntfs-3g.a` is missing, and the `UnlatchEngine` pre-build phase fails with a clear message if the library is absent — Step 02
- D-13: Engine sources compile against libntfs-3g's own `config.h` (copied by `build-ntfs3g.sh` to `build/ntfs3g/config/`, with `HAVE_CONFIG_H=1`), and the ntfs-3g headers come in through `-isystem build/ntfs3g/include` — the headers change struct layouts on `HAVE_*` macros, so they must match how the library was built; `-isystem` keeps upstream `-Wdocumentation` warnings out of our `-Werror` build — Step 03
- D-14: Open question 3 is answered: the custom `ntfs_device_operations` path works fully with `ntfs_device_mount` plus `ntfs_create_lru_caches`, with no patches. One workaround: `ntfs_volume_startup` retries read-only whenever the device's `open` returns `EROFS`, even without `NTFS_MNT_MAY_RDONLY`. So `ue_open` rejects a read-write request on a non-writable `ue_io_t` up front, and treats a volume that comes back `NVolReadOnly` as `EROFS`. The `seek` bridge must fail past `size_bytes`, because `bootsect.c` detects truncated volumes that way — Step 03
- D-15: `ue_probe` returns 0 with a verdict for every readable device (NOT_NTFS and CORRUPT included). It returns an errno only for bad arguments or ENOMEM. Severity order: HIBERNATED (active `hiberfil.sys`, or a `$LogFile` restart page 2.0 from Fast Startup or an abrupt unplug) > CORRUPT > UNCLEAN_LOG > DIRTY > CLEAN. A mount that fails behind a valid NTFS boot sector is CORRUPT (truncated, damaged MFT), not NOT_NTFS. `ue_open` never degrades to read-only: a read-write open fails with EPERM, EOPNOTSUPP or EROFS. The logfile check re-implements libntfs-3g's static `ntfs_volume_check_logfile` on top of the exported `ntfs_check_logfile` and `ntfs_is_logfile_clean` — Step 03
- D-16: The libntfs-3g log handler stays at its default (`ntfs_log_handler_null`), so the engine is silent. Routing it to OSLog category `engine` is left for the extension (Step 08) — Step 03
- D-17: The engine C tests live in `Tests/Engine/`. `Scripts/test-engine.sh` builds them with clang against the Xcode-built `libUnlatchEngine.a` (in `build/DerivedData`), makes fixture images in `build/test-engine/` with ntfsprogs plus `Tests/Engine/set_dirty.c` (a direct byte patch of `$Volume` in both `$MFT` and `$MFTMirr`), and runs the harness checks, `leaks --atExit` and a grep for the include boundary. `EngineTool/file_io.c` is the shared file-backed `ue_io_t` — Step 03
